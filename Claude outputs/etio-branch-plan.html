Three lanes, no collisions

Three vertical slices, each one a branch that compiles and demos alone. The scaffold has already been refactored so the lanes do not overlap — that refactor is the whole reason these merges can be atomic.

feat/spine Case list, event marking, live timers, Room

Strongest on Android and Compose. Also owns the build files.

feat/ai MediaPipe, ASR, classification, four-audience drafting

Most comfortable with the risky unknown. Starts first.

feat/safety WHO checklist, end-of-day report, Office Kit bridge

Steadiest. Most self-contained, most forgiving of a slow start.

Assignment

By risk, not preference.

The AI slice carries the two fatal risks in the PRD risk register: the model failing to load or OOM-ing on a loaner phone you do not control, and offline ASR mangling clinical nouns like CSSD and propofol. It gets your strongest person and the earliest start, because a failure there at hour 26 ends the project and a failure at hour 2 is just a morning.

The safety slice is fully deterministic — ChecklistStateMachine, TimerEngine and EndOfDayReportBuilder are pure Kotlin with no Android imports, no coroutines and no I/O. Most of it can be written and tested with ./gradlew testDebugUnitTest and no phone at all, which is why it survives whoever has to sleep first.

Why the lanes are actually disjoint

Three files used to be edited by all three slices. They have been split so that is no longer true.

Dependency injectiondi/ServiceLocator.kt

Was one object holding every dependency. Now a frozen shell holding the app context and clock, with CoreModule, AiModule and SafetyModule beside it — one per slice, one owner each. Dependencies point one way: AI and safety may read Core; Core reads neither.

Navigationui/EtioApp.kt

Used to declare all four destinations inline. Now calls three extension functions — spineGraph(), aiGraph(), safetyGraph() — each in a file its slice owns. Every route string lives in the frozen Routes.kt, so the spine branch can navigate to a screen the AI branch has not written yet.

The checklist gateui/caselist/CaseListViewModel.kt

Used to contain the gating logic, the dialog state and five checklist methods — safety-branch code living in a spine-branch file. All of it now sits behind ChecklistGateController, which safety owns. The spine branch's entire contact with the checklist is three calls, and that surface is a contract: if safety needs different behaviour, it changes inside the controller.

// the whole spine-to-safety interface, in CaseListViewModel + CaseListScreen
if (!checklistGate.allows(caseId, type, marked)) return@launch
checklistGate.onEventMarked(caseId, type)
ChecklistHost(viewModel.checklistGate, snackbar)

Working without the other slices

Every branch compiles and runs alone from day one, because every screen already exists as real code on main.

BranchHow you work solo
feat/spine Set AiModule.USE_FAKE_LLM = true locally — the delay path returns canned responses at realistic latency, so you design the UX against timing you will actually have. Do not commit that flip. The pre-merge script fails the branch if you do.
feat/ai The case list, live timers and five seeded cases are already on main, so you have a real case to attach a delay to on your first run.
feat/safety Your three engines are pure Kotlin. Most of this slice is built and verified with ./gradlew testDebugUnitTest — no phone, no model file, no waiting for a device.

Integration rounds

Merge at fixed points, all three of you present, one branch at a time. Never opportunistically when you happen to finish something.

WhenRoundGoal
End of first Green LightR0 — smokeEveryone merges whatever exists, even if thin. The point is proving the merge mechanics work while it is cheap.
Before Evaluation 1R1 — spine + oneThe spine plus one working delay classification. Not messages yet.
Before the Red Light rotationR2 — hardenedJob 1 validated with the OTHER fallback, checklist state machine landed. Whoever sleeps first merges first.
Feature freezeR3 — finalEverything. Nothing new merges after this — bug fixes on the demo path only.

Merge order within a round — always the same

  1. feat/spine → main No dependencies. Carries the build files and the Room schema, so everything downstream compiles against a settled base.
  2. feat/ai → main Depends on Core. Highest-risk slice, so it integrates while there is still time to back it out and try again.
  3. feat/safety → main Depends on Core. Smallest surface and no runtime coupling to the model, so it is the safest thing to land last.

The procedure

# each person, on their own branch, before the round
git fetch origin
git rebase origin/main              # rebase, not merge
bash tools/check-boundaries.sh      # must exit 0
./gradlew assembleDebug testDebugUnitTest
git push --force-with-lease

# then, one at a time, in the order above
git checkout main && git pull
git merge --no-ff feat/spine -m "Merge spine: <what landed>"
./gradlew assembleDebug testDebugUnitTest
git push

--no-ff keeps each slice as one identifiable merge commit, so git revert -m 1 <sha> backs out a whole slice cleanly if it turns out to have broken the demo path. That is the atomic part: a slice lands as one unit, or it is removed as one unit. After main is green, everyone rebases onto it again before continuing.

Pre-merge checklist

tools/check-boundaries.sh automates the first one. It is in the repo.

  • bash tools/check-boundaries.sh exits 0 — no frozen files touched, no other slice's files touched, USE_FAKE_LLM back to false.
  • ./gradlew assembleDebug testDebugUnitTest is green.
  • The app launches and your slice's demo path works on the actual loaner phone, not a dev phone.
  • You rebased onto origin/main within the last few minutes, not an hour ago.

Rules worth the friction

Rebase your branch onto main. Merge your branch into main.

Never git merge main into a feature branch. It braids the history and turns reverting a bad slice into archaeology.

Never commit the model file.

.gitignore already excludes *.task, *.bin and *.tflite. A 550 MB blob in the history cannot be removed in a hurry.

Never force-push main.

--force-with-lease on your own feature branch after a rebase is fine and expected.

Commit messages say what landed, not what you did.

“Job 1 validated JSON + OTHER fallback” beats “fix stuff”. At the fourth round you will be reading these to work out what is safe to revert.

Red Light hours produce JSON diffs, not Kotlin diffs.

Prompt, taxonomy and checklist tuning all happen in assets/config/*.json, each file owned by exactly one slice. No compiler, no merge conflict.

The full plan lives in BRANCHES.md at the repo root, alongside CODEOWNERS and tools/check-boundaries.sh. Replace the placeholder handles in CODEOWNERS with real GitHub usernames before the first push.
